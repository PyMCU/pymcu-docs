**PyMCU** compiles a statically-typed, allocation-free subset of Python directly to bare-metal
MCU machine code — no runtime, no interpreter, and no heap unless you opt into one.

Write the Python you already know — the MicroPython or CircuitPython you would write for a
Pico — and flash it to an ATmega328P (Arduino Uno), a Raspberry Pi Pico (RP2040 / RP2350)
or a PIC16 in seconds.

New here? The [PyMCU Playground](https://playground.pymcu.org/) compiles and runs code like
the samples below on an emulated Uno or Pico, right in your browser, no install needed. The
project overview, benchmarks and blog live at [pymcu.org](https://pymcu.org/).

<TabItem label="MicroPython">

```python
from machine import Pin
from utime import sleep_ms

led = Pin(13, Pin.OUT)

while True:
    led.toggle()
    sleep_ms(500)
```

</TabItem>
<TabItem label="CircuitPython">

```python
import board
import digitalio
import time

led = digitalio.DigitalInOut(board.LED)
led.direction = digitalio.Direction.OUTPUT

while True:
    led.value = not led.value
    time.sleep(0.5)
```

</TabItem>
<TabItem label="Native HAL">

```python
from pymcu.hal.gpio import Pin
from pymcu.time import delay_ms

def main():
    led = Pin("PB5", Pin.OUT)
    while True:
        led.toggle()
        delay_ms(500)
```

</TabItem>
</Tabs>

```bash
pymcu build   # → dist/firmware.hex
pymcu flash   # → avrdude upload to Arduino Uno
```

This is not Python-flavoured C: it is the same source that runs under MicroPython or
CircuitPython on a Pico, compiled ahead of time. The MicroPython and native-HAL versions
above produce **byte-for-byte identical firmware** — the compat API is a genuine zero-cost
abstraction, not a wrapper.

Pick a tab once and the whole site follows you — every example on every page switches to
the API you chose.

## Why PyMCU?

|                 | Arduino (C++) | MicroPython | CircuitPython | **PyMCU**                                           |
| --------------- | ------------- | ----------- | ------------- | --------------------------------------------------- |
| Language        | C++           | Python      | Python        | **Python**                                          |
| Runtime         | None          | Interpreter | Interpreter   | **None**                                            |
| Heap            | None          | Yes         | Yes           | **None by default** (opt-in `list[T]` arena on AVR) |
| Flash footprint | Small         | ~256 KB     | ~256 KB       | **Minimal**                                         |
| Familiar syntax | Partial       | Full        | Full          | **Full**                                            |
| Static types    | No            | No          | No            | **Yes (required)**                                  |

PyMCU occupies the gap between "write C++" and "run MicroPython": you write Python, but the
compiler produces tight machine code with zero runtime overhead — AVR and PIC assembly
emitted directly, ARM through LLVM.

For scale, the native blink above is 138 bytes on an Arduino Uno: 36 bytes for the toggle
loop and 102 bytes for the interrupt vector table. The equivalent Arduino sketch is 924
bytes with the Arduino runtime linked.

## Quick Start

### Installation

You need **Python 3.11 or newer** and [**pipx**](https://pipx.pypa.io/stable/how-to/install-pipx.html).
Starting from a machine with neither, or prefer `uv` or `pip`? The
[Installation page](/getting-started/installation/) walks through all of it.

```bash
pipx install --pip-args=--pre "pymcu-compiler[avr]"    # AVR (ATmega / ATtiny)  -- beta
pipx install --pip-args=--pre "pymcu-compiler[arm]"    # RP2040 / RP2350        -- alpha
pipx install --pip-args=--pre "pymcu-compiler[pic]"    # PIC16                  -- alpha
pipx install --pip-args=--pre "pymcu-compiler[all]"    # all of the above
```

`[avr]` is beta; `[arm]` and `[pic]` are alpha, and `[all]` installs the alpha backends
alongside the beta one. See [Supported targets](#supported-targets).

Each extra bundles its full toolchain — no system packages needed. On AVR that toolchain is
[WebAssembly](/getting-started/installation/#the-avr-toolchain-is-webassembly): one wheel that
works wherever wasmtime does.

### Create a project

```bash
pymcu new my_project
cd my_project
```

### Build and flash

```bash
pymcu build
pymcu flash --port /dev/cu.usbmodem*
```

## Supported targets

The compiler frontend and the **AVR** backend are **beta**. **ARM and PIC remain alpha**:
they build and run, but parts of the language surface are missing on them, they do not
carry AVR's continuous silicon validation, and their APIs may change between releases.

| Architecture               | Status   | Chips                                                                                                      |
| -------------------------- | -------- | ---------------------------------------------------------------------------------------------------------- |
| **AVR** (ATmega)           | **beta** | ATmega48/88/168/328P, ATmega2560, ATmega32U4                                                               |
| **AVR** (ATtiny)           | **beta** | ATtiny25/45/85, ATtiny24/44/84, ATtiny13/13A, ATtiny2313/4313                                              |
| **ARM** (Cortex-M0+ / M33) | alpha    | RP2040 (Pico / Pico W), RP2350 (Pico 2 / Pico 2 W) — PIO on both; CYW43 WiFi on the Pico 2 W (RP2350) only |
| **PIC** (mid-range)        | alpha    | PIC16F84A, PIC16F877A                                                                                      |

See [Supported Targets](/targets/) for what beta and alpha mean here, and for the
per-architecture peripheral and language coverage.

## Which API should I write?

Pick the API that matches your background — all three compile to the same bare-metal firmware.

| Package                                         | API surface                                                                                      | Status          |
| ----------------------------------------------- | ------------------------------------------------------------------------------------------------ | --------------- |
| [`pymcu-micropython`](/compat/micropython/)     | `machine` (Pin, UART, ADC, PWM, SPI, I2C, Timer, WDT), `utime`, `rp2`; `network` on the Pico 2 W | **Recommended** |
| [`pymcu-circuitpython`](/compat/circuitpython/) | `board`, `digitalio`, `analogio`, `busio`, `pwmio`, `time`, `neopixel`; `wifi` on the Pico 2 W   | **Recommended** |
| [`pymcu.hal.*`](/stdlib/)                       | Direct register-level native HAL, `@interrupt`, `asm()`, `@extern`                               | Advanced        |

Start with MicroPython or CircuitPython. They track APIs specified elsewhere rather than
defining their own, which is what makes them the surface designed to hold still, and they cost
nothing at runtime: the compiler sees through them to the same registers.

Drop to `pymcu.hal.*` when you need what the compat APIs do not expose: direct register
access, interrupt handlers, inline assembly or C interop.

:::caution[Build against a compat layer, not against the native HAL]
`pymcu.hal.*` works and is well tested, but it is deliberately low-level and it is the layer
being actively reshaped: its API **may change between releases without a deprecation cycle**.

`pymcu-circuitpython` and `pymcu-micropython` are the surfaces designed to hold still,
because they do not define their own shape — they track `digitalio` / `board` and
`machine` / `utime` as specified by CircuitPython and MicroPython. That is a reason you can
check rather than a guarantee: both packages are still pre-1.0 and the beta label covers the
compiler frontend and the AVR backend, not every API reachable through them.
:::
